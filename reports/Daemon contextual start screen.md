# Composer-first next actions replace Daemon's fixed starters

**5 October 2026 · Option B product direction approved: task-summary suggestions, exact detailed-prompt preview, immediate submission in a new chat. No per-item “Why” controls. Implementation contracts and release status remain separate.**

The owner approved **Option B: bounded, source-grounded contextual actions**, with A only as optional scaffolding. Replace the fixed prompt prefixes with **zero to three next actions beneath one composer**. Each suggestion shows a **short task summary**, with its own **detailed prompt ready before display**. Hover or keyboard focus previews the **exact prompt that will be submitted**. **Clicking or tapping the task immediately submits that prompt and its source context in a new chat**, without another Send step or returning to the source chat. This owner clarification **supersedes draft-and-wait**. The owner then removed the **Start chat badge and separate Preview button**: no redundant action tip/control remains. Touch-only users tap directly; no separate touch preview is provided. Rows retain compact source labels and dismiss/undo, but no per-item “Why” explanation: prompt preview explains what will be sent, not why an item was suggested. Internal grounding and permission checks remain required. Metadata-only **Open chat** recents remain navigation, not contextual suggestions. The [interactive study](../research_notes/Daemon%20contextual%20start%20screen/index.html) uses fictional static prompts/context and local demonstration turns, not a relevance engine or real chat API. Runtime source-resolution, cache and budget contracts remain to be designed before production implementation. Competitor evidence establishes the pattern, not a measured performance advantage over static starters.

## In-market pattern, no performance proof, and what stays undocumented

OpenAI is the reference for the requested interaction. On **14 August**, the ChatGPT release notes recorded that "eligible paid users can see homepage suggestions based on their conversation history and connected tools" ([OpenAI release notes](https://help.openai.com/en/articles/6825453-chatgpt-release-notes)). That establishes three copyable facts: a homepage surface distinct from the composer, **eligibility gating** rather than universal rollout, and two input classes — conversation history plus connected tools. It establishes nothing about mechanism. The primary's independent verification found the click behaviour, prefill-and-send path, dismissal affordance, ranking logic, and the mechanism by which GitHub data reaches a suggestion all **undocumented**, and the client identity of the observed screen unverified. Android composer suggestions updating as you type appear in an **Android subsection only** and are not evidence of general homepage behaviour, so they are not a design precedent here. Treat this as an **interaction pattern in market**, not as proof that a version of it outperforms four static starters.

Gemini's Daily Brief supplies a useful documented pattern: a proactive Gmail/Calendar/chat digest with "Top of mind" and "Looking ahead", **per-item source disclosure through the More menu**, dismiss and complete actions, helpfulness feedback and a disable switch. It is rolling out gradually to US adult personal accounts in English and requires Memory plus Workspace connections ([Gemini support](https://support.google.com/gemini/answer/17077455)). This source disclosure pattern is borrowed, not invented here. Daily Brief is a separate briefing surface, not evidence of the exact homepage rows in the supplied screenshot. OpenAI's 26 June 2026 release note announced the sunset of **Pulse**, with proactive updates migrating into scheduled tasks and a 14-day Pro transition period ([OpenAI release notes](https://help.openai.com/en/articles/6825453-chatgpt-release-notes)). An overnight briefing service is not recommended for this increment.

Claude documents **in-thread** connected-app suggestions using the current conversation plus memory, confirmation before bookings or purchases, per-chat disable/disconnect and no paid placements ([Claude connected apps](https://support.claude.com/en/articles/14730684-how-claude-suggests-connected-apps)). Its unified conversation experience is rolling out gradually to Pro and Max across web, desktop and mobile ([Claude support](https://support.claude.com/en/articles/16761823)). Consumer Copilot separates three claims: **connected service data is not used to train Copilot**, its use for personalization requires permission, and responses containing that data remain in conversation history until deleted ([Microsoft Copilot support](https://support.microsoft.com/en-us/microsoft-copilot/connecting-microsoft-copilot-to-other-services)). These statements are not a blanket promise about every response or all Copilot products. No reviewed source establishes an equivalent personalized homepage briefing for Claude or consumer Copilot; absence of documentation is not absence of a feature.

| ChatGPT | Homepage suggestions (14 Aug, paid eligible); owner's screenshot shows summary plus detailed hover prompt | Source mechanics undocumented | Screenshot shows dismiss; official mechanics undocumented | Pattern precedent plus owner-supplied observation, not signed-in testing |

GitHub is the closest documented analogue to a capability Daemon would want. Connecting GitHub to ChatGPT gives "scoped live repository read on demand", is **not** a synced index, varies by plan and surface, and is **read-only with no pushes** ([Connecting GitHub to ChatGPT](https://help.openai.com/en/articles/11145903-connecting-github-to-chatgpt)). That "read on demand, read-only, not synced" shape is the right shape for a suggestion source. **No existing GitHub connector was established by this investigation** — the inspection covered the feature registry and reviewed source paths, and `docs/FEATURE_MATRIX.md:116-117` records Projects as a placeholder with no backend API. The current proposal therefore **does not assume a GitHub connector**, and any GitHub-shaped row in a mockup is a labelled fiction.

## What Daemon can build on today

`frontend/components/WelcomeScreen.tsx:32-61` defines four static starters — Explain, Find, Compare, Draft — each a plain prompt prefix; its handler at `:71-84` appends to existing input and restores focus, **never sending**. That remains current runtime behaviour, but **is not the approved contextual-suggestion interaction**: the owner now wants immediate submission of a separate detailed prompt/context. `frontend/app/page.tsx:1252-1258` renders the welcome screen on `messages.length === 0` and wires Deliberate to an immediate `submitChat('/council')`; that behaviour is preserved unchanged pending a separate disposition decision, so the study keeps Deliberate as a quiet composer control rather than a suggestion row. The composer lives separately from the welcome screen (`frontend/app/page.tsx:1503+`), which is why the study demonstrates **one** composer relocated between a centred empty state and a docked chat slot.

The available data is real but limited. `frontend/hooks/useConversationHistory.ts:11-36` types each conversation as id, title, messages, selectedModel, timestamps, messageCount, lastActivityAt, pinned, titleLocked, status and metadata; the list fetch at `:124-162` requests `/conversations?limit=100` and populates title, timestamps, counts, pinned, status and metadata. **No semantic next step or summary field exists in that contract.** Message content arrives only via the detail fetch (`:285-315`) and switching (`:342-346`). A semantic next step therefore needs either a new backend field or client-side reading of detail messages — which is why phase 1 is a **limited bridge short of the semantic target**, not a destination. The user has not rejected personalised recents; this report simply judges them insufficient as the final answer, and the recommendation is to build them as scaffolding for the target.

One defect needs fixing in every option: a failed request calls `setConversations([])` (`useConversationHistory.ts:126-131` and the catch at `:157-160`), which renders identically to a genuine empty history. The study separates **loading** (skeleton, composer stays usable), **error** ("Daemon could not load your recent conversations", plus retry) and **new user** (nothing here is personalised). Collapsing error into empty makes a transient outage look like a statement about the user's life.

## Three options, seams, and approval boundaries

| Option | Needs | Semantic quality | Risk | Status |
|---|---|---|---|---|
| **A. Metadata-only** | Existing `/conversations` list | Titles, recency, pin, counts — no stored intent | Low code risk; untested auth-race and new UI surface | Bridge, short of target |
| **B. Bounded semantic, grounded** | Approved context contract + API/schema/capability/permission work | Real next steps, internally source-bound; compact source labels | Implementation contracts and budgeted qualified inference required | **Owner-approved target; no per-item Why UI** |
| **C. Proactive feed** | Durable tasks, scheduling, notification authority | Highest, but changes the interaction model | Cost, scheduling and authority cost dominate | Deferred |

Option A renders rows like *Open “Release notes for 2.4” — Pinned, last activity yesterday*. The MVP uses titles and recent activity only, with no stored next step claimed. It is **not** verified safe or shippable: production needs tests for the error/loading/empty distinction and **auth-generation races** — a history response resolving after an auth change must not populate rows. It needs design approval like any other option.

Option B's rules are stricter than they first look. A limited, qualified model is proposed to **generate** candidate summaries and detailed prompts; it does **not** resolve type identifiers, conversation ids or policy, and it does not decide that something is unfinished. Ordering is deterministic rules-first: eligibility (permission-filtered, non-deleted, non-restricted) → explicit user-stated intent → recency and pin → diversity, with duplicate-family suppression, a TTL and revalidation at click time. Recency alone must never imply an unfinished task; a conversation is not a commitment. Retrieved source text is **untrusted data, not authority**, and cannot grant access or override policy. Nothing executes merely on display or preview. **Click submits through the normal chat admission/execution path immediately**; any external consequence remains subject to runtime authorisation. User click authorises the request, not bypassing permissions or approval requirements.

Generation must be event-driven, not per-visit. The proposal is: a **candidate cache keyed to source-set identity and auth generation**, generated **only when the source set changes**, and reused otherwise. A **manual refresh** and an on-demand **stale** state (cache age past TTL, serving last good candidates with a visible staleness note) are the other two triggers. It explicitly does **not** call a model on every screen entry, does **not** call a model on every load, and does **not** scan message detail for all 100 listed conversations to find candidates. Exact TTL values, quota ceilings and cache invalidation semantics require design approval and are **not settled here**.

The proposed candidate record needs an allowed action type, a short task summary, its complete ready-to-submit prompt, source references with source revision/evidence time, and an expiry. Preview and submission must use **the same prompt**, not a click-time regeneration with different instructions. This is a responsibility list, **not an approved API schema**. Cache identity must include content revisions and effective scope/capability changes, not merely unchanged conversation IDs. Revalidate eligibility before showing cached rows and again at selection; an age warning never permits serving deleted, revoked or out-of-scope information. If current eligibility cannot be established, hide the personal candidate and leave ordinary chat usable.

The source-binding nuance is the one most often designed wrong. A provenance **link is not content** — linking to the Lisbon conversation does not put the Lisbon apartments into a new prompt. **Owner decision: immediately submit the suggestion's detailed prompt and source context in a new chat.** The amended prototype records that exact prompt and the source fixture's invented turns on a local demonstration user turn. Context can be inspected there. It does **not** append or send unrelated unsent composer text/files; those remain separate and are restored on Back/New chat. This illustrates content binding, but implements **no production source resolution, permissions or chat API attachment contract**. The fixtures are incomplete (for example, cancellation terms are unknown); each detailed prompt explicitly identifies relevant gaps rather than inventing facts. Production must define bounded excerpts, revisions, eligibility revalidation and how context enters the normal request without becoming instructions or silently importing unrelated history/memory. The owner's interaction choice approves behaviour, not an API/schema.

## Guardrails, failure paths, acceptance checks

Privacy is a gate, not a later phase. Tenant and auth-generation scope must be enforced **before** retrieval, render, cache and click; a stale or cross-generation result must never display. Deleting or revoking a source conversation invalidates its candidates. **Hiding personal suggestions on a private or shared screen is proposed as an initial user preference**, defaulting conservatively — **automatic shared-screen detection is not proposed and is not implemented**. Opting out must disable **generation**, not merely hide rows. Nothing goes to plaintext local storage; logs carry metadata only. Inference stays on the current qualified route, budgeted, with a **rules-only fallback** on denial or timeout. No per-keystroke calls and no hidden background work: typing **freezes** the list rather than replacing it, draft intact. "Show them anyway" temporarily reveals rows for selection; the next edit or view refresh pauses them again.

Failure paths to design and mock: no history, loading, load failure with retry, opted out, no capable provider, source deleted since render, cache past TTL, and unsent draft with attachments when navigating. Unavailable capabilities stay hidden rather than becoming hero warnings; framing stays "one general assistant", not developer tooling.

Acceptance checks: no row renders without a resolvable, existing, permission-allowed source; **hover/focus/dismiss never submits, task click submits once immediately in a new chat**; no Start chat badge or separate Preview button; submitted prompt matches the full hover preview and binds the eligible source context; unrelated unsent text/files are not sent or lost; nothing appears after opt-out or across an auth-generation change; a deleted source degrades gracefully; a provider timeout falls back to deterministic recents navigation rather than fabricated semantic tasks; no per-keystroke network call exists. Normal admission denial must preserve the user's draft and report failure rather than claiming a started chat. Metrics are **proposals requiring measured baselines first** — suggestion-start conversion, dismissal rate per row kind, undo usage, error-state frequency. No target is set before a baseline exists.

## Conclusion

**Approved direction: B, with A only as optional scaffolding; immediate new-chat submission.** Keep one composer and at most three source-grounded task summaries, each with its own detailed prompt preview and no per-item Why explanation. Click submits the exact prompt and context immediately, preserving unrelated drafts. The next step is the smallest implementation-design proposal for bounded source context, ready-prompt generation/ranking, cache, budget and normal admission contracts. Defer unclicked proactive execution until its continuity, authority and budget foundations are ready. Production implementation and release verification have not begun.
